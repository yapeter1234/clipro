# No-OBS source acquisition

This document supersedes the original OBS-first assumption for the DiegoLoveless pilot.

## Preferred Diego pilot path: Twitch Editor-authorized VOD clips

The campaign is based on Diego's Twitch channel and the user says the campaign authorizes clipping. The user is not the channel owner, and Diego will not provide an OBS/RTMPS relay.

The most robust documented Twitch path for custom editing is therefore:

1. The channel owner adds the clipper's Twitch account as a channel **Editor**, if Diego agrees.
2. The clipper authorizes Clipro's registered Twitch application with the minimum required clip-management scope: `editor:manage:clips`.
3. Clipro lists Diego's archive VODs and their metadata via Twitch Helix.
4. For a known candidate timestamp, Clipro calls `POST /helix/videos/clips` (Create Clip From VOD) with `editor_id`, `broadcaster_id`, `vod_id`, `vod_offset`, `duration`, and title.
5. Clipro polls `GET /helix/clips` to confirm the clip exists.
6. Clipro calls `GET /helix/clips/downloads` with the editor ID, broadcaster ID and clip ID to obtain a temporary media URL.
7. The worker fetches the media URL promptly, stores it in the workspace's temporary media area, and sends it to the shared AI editorial/render pipeline.
8. The resulting video is shown for user review. No publishing action is available in the MVP.

Twitch documents that the Create Clip From VOD endpoint can also clip an earlier section of a VOD that is still being generated by an active broadcast. It supports a 5–60 second clip duration. The download endpoint provides temporary URLs and requires editor/channel clip-management authorization.

Official references:
- https://dev.twitch.tv/docs/api/reference/clips
- https://dev.twitch.tv/docs/authentication/scopes/
- https://help.twitch.tv/s/article/Managing-Roles-for-your-Channel

## Important: Twitch Editor is a broad channel role

Twitch says Editors can access the channel dashboard, edit stream/video information, run commercial breaks, upload videos, start reruns, download past broadcasts, review/search/delete clips, and set clipping permissions. Only the channel owner can assign or remove the Editor role.

This is more access than a clipper strictly needs. Request it only if the creator trusts the clipper and agrees to the associated privileges. Store the user's OAuth token securely; never ask for the creator's password or stream key.

## Viewer-only fallback

If Diego does not want to assign Editor:

- Use only VOD files, excerpts or Twitch clip media explicitly supplied by Diego/campaign and permitted for the campaign.
- A viewer may be able to create a native live clip using Twitch's Create Clip API with a viewer account token containing `clips:edit`, subject to the channel's clipping/follower/subscriber settings.
- The viewer-level Create Clip permission is **not** equivalent to permission to download the media file for a custom render. Twitch's documented Get Clips Download endpoint requires `editor:manage:clips` or `channel:manage:clips`.
- If Clipro cannot obtain authorized media bytes, it must show an actionable blocker and let the user provide an authorized clip file. It must not silently fall back to undocumented playback URL extraction.

Twitch also has a channel setting that allows viewers to upload clips directly to their social accounts; Twitch says this setting is off by default. That native-share flow is not the same as obtaining a downloadable source file for Clipro's custom editing pipeline.

## Why we are not using OBS or MediaMTX for this pilot

The creator has said they cannot provide an OBS secondary feed. MediaMTX/RTMPS remains an optional ingest mode for future creators who can offer an authorized relay, but it is not a dependency for Diego's pilot.

For this pilot, Twitch is both the source platform and the permission authority. TikTok, Instagram and YouTube are possible publishing destinations only if the campaign rules permit them; publishing is outside Clipro's MVP and remains the user's manual action.

## Other platform adapters

Kick and YouTube may be supported later for metadata, live state, chat and permitted clip/file workflows. They must each implement a source-access capability matrix. Do not assume that public livestream visibility implies a supported download/edit API.
